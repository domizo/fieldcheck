# Fieldcheckの技術解説

[English](walkthrough.md) | [日本語](walkthrough.ja.md)

Fieldcheckは、架空のワークフロー実行記録の内部整合性を検査します。固定した `switchyard.run.v1` 契約、素材のハッシュ、プロバイダーの試行、承認・納品、期待結果を確認します。実モデルの品質や監査記録の真正性は検証しません。

## 検査の流れ

| コンポーネント                                   | 役割                                                                                                                                                     |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fieldcheck/__main__.py`                         | 制限付きのJSONLを読み、JSONキー・ケースIDの重複、非有限数、サイズ・深さ制限超過、不正なUnicodeを拒否する。記録の内容からコマンドを実行しない。           |
| `fieldcheck/evaluator.py` の `validate_shape`    | UTC日時、UUIDの版とバリアント、JavaScriptで安全に表せる整数、UTF-16単位の文字数を確認する。限定したv1契約の実装であり、汎用のJSON Schema解釈器ではない。 |
| `fieldcheck/evaluator.py` の `state_consistency` | 現在の入力に対する最新レビューの成功、その後の承認要求、状態と一致する監査イベントを確認する。古い入力での成功は現在のレビューの根拠にならない。         |
| 検査レポート                                     | 各条件と期待結果を記録する。終了コード0は全件合格、1は条件または期待結果の不一致、2は入出力エラー。                                                      |

## 設計判断

| 判断                             | 理由と保証の範囲                                                                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Pythonの実行環境を独立させる     | 境界はJSONL。Node、UI、サーバー、APIキー、実行時の外部パッケージなしで動く。                                               |
| 監査イベントと状態を対応付ける   | レビュー結果が存在するだけでは、現在の入力でプロバイダーが成功したとは言えない。関連するイベントで矛盾した履歴を検出する。 |
| JavaScriptの値の制限に合わせる   | データを作る側の契約に合わせる。Pythonの整数や文字数だけで判定すると、TypeScript側では拒否する値を受け入れることがある。   |
| 整合性と真正性を分ける           | 内部的に整合する偽の署名なし記録は合格し得る。認証や署名には別の信頼設計が必要。                                           |
| 既知のフィクスチャ結果を検査する | 同梱ケースは期待する状態と障害結果が明示されている。時間はローカル処理の測定であり、実モデルの推論速度や品質ではない。     |

## 再現できる検証

[READMEの実行コマンド](../README.ja.md#実行方法)で、ベースラインと意図的に壊したデータを検査できます。想定された障害は期待結果に一致すれば合格し、矛盾した実行記録は条件違反として不合格になります。テスト対象は、素材・ダイジェストの改変、古い承認、存在しない素材への参照、拒否後の切り替え、現在の入力に対するレビューと判断の順序、値の制限、不正なUnicodeです。

契約検証の回帰テストでは、修正前に不正な値の受け入れとUnicodeによる異常終了を再現し、修正後に合格することを確認しました。コマンド、測定結果、検証範囲は[検証記録](verification.md)にまとめています。

## 制約

Fieldcheckが検査するのは出力された納品ファイル一覧とハッシュです。実際のファイル内容は、Switchyardの結合テストとダウンロードAPIが検証します。汎用のJSON Schema解釈、署名付き監査記録の検証、実モデルの採点、統計的な品質推定、クラウドへのレポート保存は未実装です。形式とイベントの内部整合性が正しくても、内容が事実として正しいことは証明できません。固定した形式とハッシュの規則は[データ契約](contract.md)に記載しています。
